# Screener 專案棕地增強 PRD

## 第一部分：專案分析與背景

### 1.1 現有專案總覽

*   **分析來源**: 基於 Winston 產出的 `docs/brownfield-architecture.md` 文件以及我們的對話。
*   **專案現況**: 此專案目前是一個 Python 腳本集合，用於從多個交易所下載金融數據，並執行數個獨立的策略來篩選強勢的股票與加密貨幣。主要產出是可匯入 TradingView 的標的列表。

### 1.2 Enhancement Scope Definition

*   **增強類型**: 這是一次「新功能添加」與「重大功能修改」，並需要進行「架構更改」。
*   **增強描述**: 本次目標是重構現有雜亂的程式碼，並增加一個新的交易模組。此模組能根據 15 分鐘 K 線的均線訊號，模擬開倉、管理倉位並計算盈虧，最後將結果透過 Webhook 發送到 Discord。
*   **影響評估**: 這是一次「重大影響 (Major Impact)」，因為它需要對現有架構進行重構。

### 1.3 目標與背景

*   **目標**:
    *   將現有重複的策略邏輯抽象化，提高程式碼的可維護性與可擴展性。
    *   建立一個自動化的交易信號執行與通知流程。
    *   建立一個可追蹤模擬倉位盈虧的系統。
*   **背景**: 現有專案已能成功篩選標的，但程式碼結構混亂，難以擴展新策略或加入交易執行等下游應用。本次重構與功能增強是為了讓專案從一個單純的「篩選器」演進為一個半自動化的「交易信號系統」。

## 第二部分：需求 (Requirements)

### 功能性需求 (Functional Requirements)

*   **FR1**: 現有的三個策略腳本 (`ttt`, `crypto_relative_strength`, `stock_screener`) 必須被重構為一個統一、模組化的策略框架。每個策略應成為此框架下的一個可獨立設定和執行的模組。
*   **FR2**: 系統必須能夠獲取強勢標的列表，並針對列表中的每個標的，抓取 15 分鐘的 K 線數據。
*   **FR3**: 系統必須能夠根據 15 分鐘 K 線的均線交叉訊號，產生「開倉」或「平倉」的交易訊號。
*   **FR4**: 系統必須能夠模擬一個預設大小的倉位，並根據交易訊號追蹤其開倉價格、目前狀態與即時盈虧 (PnL)。
*   **FR5**: 系統必須能夠在產生交易訊號或倉位盈虧更新時，透過 Webhook 將結構化的訊息發送到指定的 Discord 頻道。
*   **FR6**: 所有策略參數、API 金鑰和 Webhook URL 等設定，都必須從一個統一的外部設定檔 (`config.py` 或 `.env`) 中讀取，而非寫死在程式碼中。

### 非功能性需求 (Non-Functional Requirements)

*   **NFR1**: 重構後的程式碼必須遵循關注點分離 (Separation of Concerns) 原則，將數據獲取、策略分析、交易執行和通知等功能明確分離到不同的模組中。
*   **NFR2**: 核心業務邏輯（如策略計算、倉位管理）必須包含單元測試，以確保程式碼的穩定性與正確性。
*   **NFR3**: API 金鑰等敏感資訊不得提交到版本控制系統中。
*   **NFR4**: 重構後的系統在執行現有篩選強勢標的的功能時，其產出結果應與重構前保持一致。

### 相容性需求 (Compatibility Requirements)

*   **CR1**: 系統必須維持與現有數據源 (Binance, Bybit, OKX, Polygon.io) 的 API 相容性。
*   **CR2**: 系統應保留將篩選結果輸出為 TradingView 相容格式的功能，即使這不是新交易流程的主要路徑。
*   **CR3**: 新系統必須能在與現有專案相同的 Python 環境及依賴套件下運作。

## 第三部分：技術限制與整合需求

### 3.1 現有技術堆疊

*   **語言**: Python 3.x
*   **框架/函式庫**: Pandas, NumPy, python-binance, ccxt, yfinance, TA-Lib, APScheduler
*   **資料庫**: 無 (本地檔案系統，如 .csv, .txt)
*   **基礎設施**: 本地機器執行
*   **外部依賴**: Binance API, Bybit API, OKX API, Polygon.io API, Discord Webhook API

### 3.2 整合方法

*   **資料庫整合策略**: 專案將繼續以檔案為基礎，但會考慮將策略設定、交易紀錄等結構化數據存儲在輕量級的本地資料庫 (如 SQLite) 中，以利於查詢和管理。
*   **API 整合策略**: 將維持與現有金融數據 API 的連接。新的 Discord 通知功能將透過 `discord-webhook` 函式庫與其 API 整合。
*   **前端整合策略**: 無。
*   **測試整合策略**: 將引入 `pytest` 框架。為新的核心模組 (如策略、交易、通知服務) 建立單元測試，並在 CI/CD 流程中自動執行 (若未來導入 CI/CD)。

### 3.3 程式碼組織與標準

*   **檔案結構方法**: 將採用新的模組化結構，如下所示：
    ```
    screener/
    ├── main.py             # 應用程式主入口
    ├── config.py           # 統一設定檔
    ├── data/               # 數據獲取與轉換模組
    ├── strategy/           # 策略模組
    ├── services/           # 交易與通知等服務
    ├── tests/              # 測試程式碼
    └── requirements.txt
    ```
*   **命名慣例**: 類別名稱使用 `PascalCase`，函式與變數使用 `snake_case`。
*   **編碼標準**: 遵循 PEP 8 編碼風格指南。
*   **文件標準**: 核心函式與類別需包含標準的 docstrings，解釋其功能、參數與回傳值。

### 3.4 部署與維運

*   **建置流程整合**: 無需編譯。
*   **部署策略**: 直接透過 `git pull` 更新程式碼，並透過 `pip install -r requirements.txt` 安裝依賴。
*   **監控與日誌**: 引入 Python 的 `logging` 模組，將重要的應用程式事件（如任務開始/結束、交易訊號、API 錯誤）記錄到日誌檔案中。
*   **設定管理**: 所有環境相關的設定（API 金鑰、Webhook URL）將透過 `.env` 檔案進行管理，並使用 `python-dotenv` 函式庫載入。

### 3.5 風險評估與緩解

*   **技術風險**:
    *   **風險**: 現有程式碼缺乏測試，重構過程可能引入未預期的錯誤，破壞原有功能。
    *   **緩解**: 在重構前，先為現有策略的輸入和輸出建立基準測試 (golden tests)。重構後的模組必須通過這些測試，確保行為一致。
*   **整合風險**:
    *   **風險**: 外部 API (例如交易所) 可能會變更、限制請求頻率或變得不穩定。
    *   **緩解**: 在 API 客戶端中實作健全的錯誤處理與重試機制 (例如使用 `tenacity` 函式庫)。
*   **部署風險**:
    *   **風險**: 手動部署過程容易出錯。
    *   **緩解**: 撰寫一個簡單的部署腳本 (`deploy.sh`) 來自動化更新與啟動流程。

## 第四部分：史詩與故事結構

### 史詩 1：篩選器 V2：核心重構與交易訊號自動化

*   **史詩目標**: 將現有的篩選器腳本重構成一個健壯、模組化、易於擴展的應用程式，使其能夠自動執行交易策略、產生訊號、管理模擬倉位，並發送通知。
*   **整合需求**: 新系統必須與現有的數據源（Binance, Polygon 等）和通知渠道（Discord）無縫整合，同時為未來擴展新策略或交易模組提供清晰的路徑。

### 建議的使用者故事序列 (User Story Sequence)

1.  **故事 1：核心架構重構**
2.  **故事 2：現有策略模組化**
3.  **故事 3：交易訊號產生與通知**
4.  **故事 4：15 分鐘線圖交易邏輯實作**
5.  **故事 5：模擬倉位與盈虧管理**
